## What slipped
The factory filed an architecture cleanup issue from an allowlist entry, and the implementer stopped as BLOCKED at Task 1, before any PR or gate run. The issue body named the wrong pattern. It said `fail-closed`, but the architecture skill lists `stripe-outside-billing` as the mechanical check of `aggregate-root` (Stripe money calls belong in Billing). The body also did not say where the fix goes. The payroll reference says the violation "awaits a move into services/billing*", and both the source file and its destination are protected paths. So the implementer had a cross-context design choice with several valid answers and nothing in the issue to point it to one. It stopped as its rules tell it to. The pattern is not the only gap: in the same table, `fetch-outside-api` is mapped to `anti-corruption-layer` when the skill puts it under `thin-router`.
## Why the gate missed it
No gate covers this. The issue text is built by factory/proposals.py from a hand-written `_PATTERN` table that has drifted from .claude/skills/architecture/SKILL.md, and no test checks the two against each other. The issue also has no slot for where the fix should go. Gates only review diffs, so nothing ever checked the issue the implementer was given.
## Proposed change
(mechanical-test) Add a factory test in factory/tests/test_proposals.py that parses .claude/skills/architecture/SKILL.md. For each pattern section it reads the rule ids in the backticks on that section's "Mechanical check" line, then asserts that `proposals._PATTERN[rule]` names the pattern whose section lists that rule. It also asserts that every rule in `_PATTERN` appears in exactly one section. With this test, the drift between the cleanup-issue generator and the skill fails `pytest factory/tests` instead of reaching an implementer. Fixing the two wrong mappings (`stripe-outside-billing` to `aggregate-root`, `fetch-outside-api` to `thin-router`) is needed to make it pass.
