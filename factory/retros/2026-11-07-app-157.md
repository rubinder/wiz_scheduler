## What slipped
Triage judged the epic too big and posted a sensible five-part split. The block comment told the owner to reply to retry, so the owner replied to approve the split. That reply bought one retry. Triage ran again, reached the same too_big verdict, noted that the owner had approved the split, and still posted the same proposal again, asking the owner to create the sub-issues by hand. The retry was spent without moving the work forward. The issue is now blocked a second time, with the same text, and the owner's approval has nowhere to go.
## Why the gate missed it
No gate covers this. Gates only review diffs, and this run stopped at triage before any code existed. The gap is in the workflow itself. In .claude/workflows/issue-pipeline.js, too_big only ever leads to block(), and nothing in the pipeline can file sub-issues. The issue-triager agent has three verdicts (workable, too_big, needs_answers) and none of them means "the owner accepted my earlier split". The shared reply note ("To retry, reply here") is appended to every block comment, including too_big ones. A reply there cannot change the verdict, so any owner answer to a split proposal re-blocks with the same text.
## Proposed change
(skill-rule) Add a rule to .claude/agents/issue-triager.md: when the factory's latest comment on the issue is a too_big split proposal and a later owner comment accepts it, return a new verdict `split_approved` with the decomposition. Each part gets a target repo (app or marketing), a title and a body, and the parts keep their order. Edit any parts the owner asked to change, and leave out any the owner rejected. In .claude/workflows/issue-pipeline.js, handle `split_approved` the way factory-propose.js files issues. Write each title and body to a file with the Write tool. Create each sub-issue in its target repo, label it `agent-ready` (the owner approved it), and record its dependencies as "Depends on #n" in its body. Then post one tracker comment that links the new issues and does not block again. For too_big blocks, change the reply note to say that replying "approved" (or naming the parts to keep) files the sub-issues. Add a factory test in factory/tests/ that checks that the too_big path and the `split_approved` path never produce the same comment, so an approval can't loop back into the same proposal.
